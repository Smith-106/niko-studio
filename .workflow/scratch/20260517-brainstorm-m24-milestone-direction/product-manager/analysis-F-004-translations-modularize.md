# F-004: Translations Modularize — Product Analysis

## User Value Proposition

将 2892 行的单体翻译文件按功能模块拆分，改善开发体验，减少合并冲突，为未来多语言扩展和社区翻译贡献铺路。用户将受益于更快的功能迭代速度（间接）和未来更完善的多语言支持。

**核心价值**: 开发效率 + 可维护性 + 多语言扩展基础

## Priority Justification

### Impact vs Effort Matrix

| 维度 | 评估 |
|------|------|
| 用户影响 | Low（当前仅中英文） |
| 开发影响 | High（减少合并冲突，加速 i18n 流程） |
| 架构影响 | Medium（建立模块化 i18n 范式） |
| 实施工作量 | Medium（需设计模块边界 + 迁移） |
| 风险 | Low（key 结构不变，纯文件组织调整） |

**综合优先级**: P2 — 开发体验改善显著，SHOULD 在 Batch 2 完成。

## Success Metrics

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 单文件最大行数 | < 300 行 | 静态分析 |
| 模块数量 | 8-12 个（按功能域） | 文件计数 |
| 翻译 key 完整性 | 100%（拆分前后一致） | 自动化对比脚本 |
| 合并冲突频率 | 降低 80%+ | Git 历史统计 |
| Tree-shaking 效果 | 未使用模块不打包 | Bundle 分析 |

## User Stories

### US-001: 作为开发者，我希望修改某个功能的翻译时不影响其他模块
**动机**: 当前任何翻译修改都在同一个 2892 行文件中，频繁产生合并冲突
**验收**: 修改评估面板翻译只需编辑 `translations/evaluation.ts`

### US-002: 作为开发者，我希望新增功能模块时翻译文件自动隔离
**动机**: 新功能的翻译不应与现有翻译混在一起
**验收**: 新模块翻译在独立文件中定义，通过统一入口注册

### US-003: 作为产品经理，我希望未来能支持社区贡献翻译
**动机**: 模块化后，社区可以针对单个模块提交翻译 PR，降低贡献门槛
**验收**: 每个翻译模块有独立的类型定义，缺失 key 有编译时提示

## Acceptance Criteria

1. translations.ts MUST 拆分为按功能域组织的独立模块文件
2. 拆分后所有翻译 key MUST 与拆分前完全一致（自动化验证）
3. 每个模块文件 SHOULD NOT 超过 300 行
4. MUST 保留统一的类型安全入口（`t('module.key')` 有类型提示）
5. 模块加载 SHOULD 支持按需导入（tree-shakable）
6. MUST NOT 改变现有组件中翻译函数的调用方式
7. 所有现有测试 MUST 通过
