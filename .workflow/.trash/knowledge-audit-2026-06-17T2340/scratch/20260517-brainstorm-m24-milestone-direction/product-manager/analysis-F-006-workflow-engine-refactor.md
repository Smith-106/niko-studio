# F-006: Workflow-Engine Refactor — Product Analysis

## User Value Proposition

将 1970 行的 workflow-engine 单文件重构为分层架构（编排层 + 业务规则层 + 执行层），降低新功能开发成本，提升工作流执行的可靠性和可观测性。用户将受益于更稳定的分析任务执行和更快的新功能交付节奏。

**核心价值**: 架构可扩展性 + 开发效率 + 运行稳定性

## Priority Justification

### Impact vs Effort Matrix

| 维度 | 评估 |
|------|------|
| 用户影响 | Low-Medium（稳定性改善） |
| 开发影响 | Very High（新功能开发效率倍增） |
| 架构影响 | Very High（核心引擎现代化） |
| 实施工作量 | High（需仔细设计分层 + 全面测试） |
| 风险 | High（核心模块，回归风险大） |

**综合优先级**: P2 — 架构价值极高但风险也高，MUST 严格限定接口不变，SHOULD 在 Batch 3 执行。

## Success Metrics

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 单文件最大行数 | < 400 行 | 静态分析 |
| 模块数量 | 4-6 个（按职责分层） | 文件计数 |
| 公共 API 变更 | 0（完全兼容） | API diff 工具 |
| 测试覆盖率 | >= 拆分前 + 新增单元测试 | Coverage report |
| 工作流执行正确性 | 100% 现有场景通过 | 集成测试 |
| 新任务类型添加工时 | < 2 小时（vs 当前 1 天+） | 开发者反馈 |

## User Stories

### US-001: 作为开发者，我希望添加新的分析任务类型只需实现一个接口
**动机**: 当前添加新任务需要修改引擎核心逻辑，风险高且耗时
**验收**: 新任务类型通过实现 TaskHandler 接口 + 注册即可工作

### US-002: 作为用户，我希望分析任务失败时能看到清晰的错误信息
**动机**: 当前引擎错误处理混杂在业务逻辑中，错误信息不够用户友好
**验收**: 任务失败时显示具体原因和建议操作，而非技术堆栈

### US-003: 作为开发者，我希望能独立测试工作流编排逻辑
**动机**: 当前编排和业务规则耦合，测试需要 mock 大量依赖
**验收**: 编排层可独立单元测试，不依赖具体业务规则实现

## Acceptance Criteria

1. workflow-engine MUST 拆分为至少 3 层：编排（orchestration）、规则（rules）、执行（execution）
2. 现有公共 API MUST 100% 向后兼容（接口签名不变）
3. 所有现有工作流场景 MUST 通过集成测试验证
4. 每层 MUST 有独立的单元测试，覆盖率 SHOULD >= 80%
5. MUST NOT 引入新的外部依赖
6. 重构 MUST NOT 改变工作流执行的可观测行为（日志、事件、状态转换）
7. SHOULD 提供 TaskHandler 接口供新任务类型注册
8. 重构范围 MUST NOT 超出 workflow-engine 模块边界

## Dependencies and Sequencing

### 前置依赖
- F-001 SHOULD 先完成（logger 规范确立）
- 无硬性技术依赖，但建议在其他低风险项完成后执行

### 后续影响
- F-007 叙事可视化的数据管道 SHOULD 利用重构后的引擎接口
- F-008 修订工作流 MUST 依赖重构后的 TaskHandler 扩展点
- 写作会话智能（M25 候选）需要引擎支持实时任务类型

### 建议排期
- **Batch 3, Week 6-7**
- 预估工时：5-7 天（含全面测试）
- MUST NOT 与其他高风险项并行
- 建议设置"接口冻结"检查点：重构开始前锁定公共 API 签名

### 风险缓解

| 风险 | 缓解措施 |
|------|----------|
| 范围蔓延 | 严格限定：只拆分，不加功能 |
| 回归 | 先写集成测试覆盖现有行为，再重构 |
| 接口变更 | 重构前导出 API 快照，重构后自动对比 |
| 性能退化 | 重构前后 benchmark 对比 |
