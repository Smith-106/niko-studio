# Cross-Cutting Analysis: M24 Product Decisions

## Milestone Scope Recommendation

### M24 纳入范围（MUST + SHOULD）

| Priority | Features | 理由 |
|----------|----------|------|
| P1 MUST | F-001, F-002 | 低风险高确定性，直接改善开发体验和运维能力 |
| P2 SHOULD | F-003, F-004, F-005, F-006 | 代码健康度提升，为新功能开发扫清障碍 |
| P3 SHOULD | F-007 | 唯一纳入的新功能方向，用户感知度高 |

### M25 延期（MAY）

| Feature | 延期理由 |
|---------|----------|
| F-008 智能修订工作流 | 依赖 F-006 重构完成；需要更多用户反馈验证 M23 读者模型的实际使用模式 |
| 写作会话智能 | 需要行为数据积累，当前缺乏基线数据 |
| 写作知识个性化 | 依赖 F-005 catalog 外置完成后的数据架构 |

## User Impact Assessment

### 直接用户感知

- **F-007 叙事可视化**: 用户可直接看到、交互的新功能，感知度最高
- **F-002 组件拆分**: 间接改善 UI 响应速度，用户可能感知到性能提升
- **F-001 Console 收口**: 用户完全无感，但减少生产环境信息泄露风险

### 开发者体验（DX）改善

- **F-004 翻译拆分**: 减少合并冲突，加速 i18n 工作流
- **F-003 类型安全**: IDE 提示更准确，减少运行时调试
- **F-006 Engine 重构**: 新功能开发效率提升 30-50%（估算）

### 长期战略价值

- **F-005 Catalog 外置**: 为社区贡献、用户自定义知识库铺路
- **F-006 Engine 重构**: 为 M25+ 复杂工作流（修订、会话智能）提供基础
- **F-008 修订增强**: 将 M23 的分析能力转化为可操作的修订指导

## Release Strategy

### 推荐：增量交付（3 个批次）

**Batch 1（Week 1-2）: Quick Wins**
- F-001 Console 收口
- F-003 as any 清理
- 交付标准：所有现有测试通过，无新增 console.* 或 as any

**Batch 2（Week 3-5）: Structural Improvements**
- F-004 翻译模块化
- F-002 巨型组件拆分
- F-005 Craft-Catalog 外置
- 交付标准：组件测试覆盖率不降，翻译 key 结构不变

**Batch 3（Week 6-8）: Architecture + New Feature**
- F-006 Workflow-Engine 重构
- F-007 叙事结构可视化（MVP）
- 交付标准：现有工作流 API 100% 兼容，可视化基础功能可用

### 为什么不用 Big-Bang

1. 技术债清理天然适合增量交付——每项独立可验证
2. 降低回归风险——问题可快速定位到具体批次
3. 团队获得持续正反馈——每 2 周有可见进展
4. F-007 依赖 F-002 组件拆分的架构改善，自然排在后面

## Feature Interaction Map

```
F-001 Console ─────────────────────────────────── (独立)
F-003 Type Safety ─────────────────────────────── (独立)
F-004 Translations ────────────────────────────── (独立)

F-002 Component Split ──┬── F-007 需要 Panel 架构清晰
                        └── F-008 修订 UI 需要可扩展的面板结构

F-005 Catalog Externalize ──┬── F-008 修订建议需要外置的知识数据
                            └── 写作知识个性化（M25）依赖此

F-006 Engine Refactor ──┬── F-007 可视化的数据管道依赖清晰的引擎接口
                        └── F-008 修订工作流需要引擎支持新任务类型
```

### 关键依赖链

1. F-002 SHOULD 在 F-007 之前完成（Panel 架构清晰后再加新面板）
2. F-006 SHOULD 在 F-007 之前完成（引擎接口稳定后再接入可视化数据流）
3. F-005 MAY 与 F-007 并行（无直接依赖）
4. F-001, F-003, F-004 之间无依赖，MAY 并行执行

## Decision: 新功能方向选择

### 选择 F-007（叙事可视化）而非 F-008（修订增强）的理由

| 维度 | F-007 叙事可视化 | F-008 修订增强 |
|------|-----------------|---------------|
| 用户感知 | 极高（可视化界面） | 中等（流程改善） |
| 技术依赖 | F-002 组件拆分 | F-005 + F-006 |
| MVP 可行性 | 高（时间轴 + 张力曲线即可交付） | 低（需完整修订循环） |
| 差异化价值 | 市场上少见 | 竞品已有类似功能 |
| M23 承接 | 利用现有分析数据 | 深度依赖读者模型 |

**结论**: F-007 在 M24 时间框架内更可控，且能为产品带来明显的差异化竞争力。F-008 SHOULD 在 M25 中作为重点方向，届时 F-005 和 F-006 已完成，技术基础更扎实。
